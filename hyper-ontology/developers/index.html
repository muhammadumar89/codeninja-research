Quickstart
Model your operation in Hyper Studio, publish, and export. What you download is a complete, typed backend with the ontology inside it. A few commands stand it up.
terminal
# 1. In Hyper Studio: Code, Export project (backend)
$ unzip mining-gold-project-backend.zip && cd mining-gold-project
$ cp .env.sample .env        # your Postgres, your secrets
$ npm install
$ npm run migrate            # create the schema
$ npm run seed               # optional sample records
$ npm run dev
# API     http://localhost:8000
# Agents  http://localhost:8000/mcp
# Docs    http://localhost:8000/api-docs

src/mcp/manifest.ts · the shape of every object
export interface OntologyObject {
  apiName: string;
  displayName: string;
  description: string;
  synonyms?: string[];        // the names the business really uses
  semanticDomain?: string;    // authored business domain
  labelProperty?: string;     // what identifies a record to a person
  properties: OntologyProperty[];
  links: OntologyLink[];
  lifecycles?: OntologyLifecycle[];          // kinetics
  derivedStatuses?: OntologyDerivedStatus[]; // computed on read
  actions?: OntologyAction[];                // business actions
  functions?: OntologyFunction[];            // analytics by name
  sideEffects?: OntologySideEffect[];
  agentAccessible: boolean;
}
Generated, never hand editedStudio is the source of truth for what things mean. The manifest is its derived layer, rebuilt on every publish.
Typed end to endObjects, links, lifecycles and functions are TypeScript types your editor and your agents both understand.
A report on every buildgeneration-report.json lists every decision the generator made and why.
Elsewhere
The ontology is a configuration in someone else's database. There is no file to review, and no history you control.
synonyms · links
Semantics
Semantics write down what every object means, in the words the business uses. The Mining GOLD Copper ontology carries 18 objects, 46 typed links and 37 synonyms, so an agent asked about a repair ticket finds the Maintenance Work Order without a lookup table.
  1. Object: an apiName, a display name, a description and a labelProperty people recognise.
  2. Synonyms and domain: synonyms for every other name, semanticDomain for where it belongs.
  3. Links: a cardinality, the property that stores it, a phrase that reads as a sentence, and via, the tool that walks it.

src/kinetics/
Kinetics
Kinetics model how the operation moves. A lifecycle names the states a record can be in and the transitions between them. Each transition is generated as its own function: it locks the row, checks the move is allowed, and commits in one transaction. Ordinary updates are stripped of the governed field, so a transition is the only way the state can change.
src/kinetics/maintenanceWorkOrder.ts
// src/kinetics/maintenanceWorkOrder.ts (generated, do not edit by hand)
export const transitionMaintenanceWorkOrderAssign = async (params, input = {}, actor = null, opts = {}) => {
  const run = async (t) => {
    const wo = await MaintenanceWorkOrder.findOne({ where: { id: params.id }, transaction: t, lock: t.LOCK.UPDATE });
    if (!wo) throw notFound('MaintenanceWorkOrder', 'INVALID_MAINTENANCE_WORK_ORDER_ID');
    if (wo.orderStatus !== 'unassigned') {
      throw badRequest(`Cannot 'Assign': orderStatus is '${wo.orderStatus}', allowed from: unassigned`, 'KINETICS_INVALID_TRANSITION');
    }
    return wo.update({ orderStatus: 'assigned' }, { transaction: t });
  };
  return opts.transaction ? run(opts.transaction) : sequelize.transaction(run);
};

// ordinary updates can never touch a governed state
export function stripMaintenanceWorkOrderGovernedFields(payload) {
  delete payload.orderStatus;
}
Initial and terminal statesA new work order starts unassigned. completed and cancelled end it.
Role gatedEvery transition carries a permission. A person and an agent pass the same check.
One error for every bad moveKINETICS_INVALID_TRANSITION, with the states it was allowed from.
Try it: move a work order through its lifecycle.
Elsewhere
Actions are buttons wired in a hosted builder. Nothing stops a script that writes the field directly.
functions · actions
Functions and actions
Functions are the numbers the operation runs on, computed once on the server and callable by name: collection insights and dashboard measures. Actions are business operations that are neither plain edits nor lifecycle moves, each fired by a named tool, with a precondition and a flag for the ones that need a person to confirm. Derived statuses are computed on read and arrive on every row as _derived.<key>.
functions in the manifest

src/mcp/gateway.ts
Agents over MCP
Every export serves the ontology to agents at /mcp. The gateway registers four meta tools however large the ontology grows, so an agent discovers what it needs instead of loading hundreds of tools. Access is fail closed: search results and manifest objects are filtered by the caller's role, and properties a role cannot see are hidden from the ontology too.
what an agent calls
// The gateway registers four meta tools, whatever the size of the ontology:
//   describe-project   what every object IS, how objects link, kinetics, functions
//   search-tools       the tools this caller may use, filtered by role
//   get-tool-schema    the JSON input schema of one tool
//   invoke-tool        validate the arguments and run the tool

// an agent, before it acts
{ "method": "tools/call", "params": { "name": "describe-project" } }
{ "method": "tools/call", "params": { "name": "search-tools", "arguments": { "query": "work order" } } }
{ "method": "tools/call", "params": { "name": "invoke-tool",
  "arguments": { "tool": "assignMaintenanceWorkOrder", "args": { "id": "…" } } } }
Hyper Pragma's agents work exactly this way: they call describe-project before they act. See them at work.

Atlas
Atlas connects the systems you already run to the ontology, in place. Add a source, map its fields to objects and properties, choose how it stays in step, and approved changes write back. Nothing is migrated, and the source system stays the system of record.

Records stay in the source system. Atlas maps them onto objects, keeps them in step and writes approved changes back.
  1. Connect a source: databases, ERP and maintenance systems, message streams, file shares and spreadsheets.
  2. Map: each source field to an object property, or to a link between objects.
  3. Keep in step: live, on a schedule, or on event, per source.
  4. Write back: a transition approved in the ontology is written to the system that owns the record.
Elsewhere

Studio · Agents
Agentic Studio
Agentic Studio is where you build the agents that work on the ontology: bind each one to the objects it serves, give it a schedule and a role, and turn on Self Improving Memory, so every run is graded against its own instructions and the agent keeps what it learned. When you publish, the agents export with the application, beside manifest.ts, and you run them yourself.

Dockerfile
Run it anywhere
The export is a standard Node.js service on Postgres, with a Dockerfile, migrations and an OpenAPI description. Run it on premises, in your private cloud or air gapped, beside models you host yourself.
production
$ npm run build && npm start          # or: docker build -t mining-ontology .
# Postgres of your choice, inside your network
# one instance behind /mcp until a shared token store is configured
# no call leaves your walls: models, agents and data stay where you run them
